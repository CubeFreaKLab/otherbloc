# Local load verification

The measured workload is anonymous editorial reading through gateway port 3000, with real Users, Content, Interactions, Firestore and Storage. It is not a health-endpoint benchmark, a browser rendering score, a write-load test or a cloud-capacity claim.

## Run

Install [Grafana k6](https://grafana.com/docs/k6/latest/set-up/install-k6/) separately; the verified binary is v2.2.0. Put it on `PATH`, or set `K6_BINARY` to its executable path in the invoking terminal. The npm lockfile does not install k6.

Start the local emulators, all four backend applications with `node scripts/dev.mjs --no-watch`, and both demo seeds as described in [development](development.md). Then, from the repository root:

```bash
node scripts/load.mjs --smoke
npm run test:load
```

Smoke means **one** virtual user and one iteration, never acceptance at 50 users. The normal command fixes 50 virtual users for 60 seconds; unknown arguments fail. It accepts only the local demo configuration, loopback gateway and complete published demo dataset. No accounts, credentials, publication bodies or interaction writes are generated by the load runner.

Each execution creates a fresh ignored `.local-data/load-<mode>-<timestamp>/` directory containing `environment.json`, `dataset.json`, complete k6 `summary.json`, console `output.txt`, and `result.json` with the actual exit code. The environment identifies the base commit, tracked modifications, hashes of the workload scripts, versions, hardware, options and configured gateway limits. Keep these private; do not commit generated results. A failing threshold retains its evidence and returns a nonzero exit code.

Do not run build, integration, browser or Lighthouse suites during the measurement. Keep the gateway's security limits unchanged. Its normal 18,000-request/15-minute window includes earlier requests from the same address; allow that window to expire before another full run if the accumulated traffic would exceed it. A genuine 429 is an error in this workload, not an excluded sample.

## Workload and checks

A [constant-VU executor](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-vus/) runs a closed workload: each user makes these four requests sequentially, then waits one second as reader think time. That pause contributes to iteration duration, not HTTP latency. Seven actual `demo=true` publications and four authors are discovered from the public API before timing. Publication selection rotates deterministically across users and iterations.

| Name | Gateway request | Actual work checked |
| --- | --- | --- |
| publications | `GET /api/publications?limit=12` | The seven published demo readings are present |
| profiles | `GET /api/users/profiles?ids=<four IDs>` | Current public profiles for all four authors |
| composition | `POST /api/interactions` | Publication/body and author from their owning services, up to five comments, real counters and anonymous relation state |
| media | `GET /api/publications/<id>/media/<coverId>?width=640` | Nonempty WebP bytes from Storage via Content |

There is no browser cache or extra shared application cache introduced for the measurement. HTTP keep-alive remains enabled. Health/dataset preflight requests occur before k6 and are not benchmark samples. The scenario permits up to ten seconds to finish iterations already started at the 60-second boundary; it does not start another ten seconds of load.

[Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) require P95 below 400 ms globally **and independently for all four routes**, zero failed HTTP requests, and 100% of business checks. HTTP 200 with GraphQL errors fails. Invalid JSON, missing content/authors and invalid image bodies fail as well. Redirects are not followed. The raw summary is preserved using [handleSummary](https://grafana.com/docs/k6/latest/results-output/end-of-test/custom-summary/); the console shows a smaller subset without changing the measured data.

## Verified result — 2026-09-07

Run started at 19:27:20.970 UTC, based on `170582b` plus the workload scripts identified by hashes in its environment record. k6 v2.2.0, Node v24.14.1, Windows 10.0.26220, Intel Core i7-10700, 16 logical CPUs and 34,257,453,056 bytes of RAM. All required thresholds pass for this local reading workload. The small seeded dataset, warm long-lived service connections, same-host networking and one-second think time limit what can be inferred. This does not establish maximum throughput, high-cardinality feeds, comment-heavy readings, authenticated writes, long-duration stability or Render/Firebase production performance. Those environments need their own authorized measurements.

The first smoke diagnostic failed the image checks because the new test incorrectly sent `w=640`; the API correctly rejected that unknown parameter. The script was corrected to the existing `width=640` contract, and the next smoke passed all eight checks before the full run. Both outputs are retained separately. No application behavior or security threshold was relaxed to achieve the result.
